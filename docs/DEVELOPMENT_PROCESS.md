# BuyJudge 개발 프로세스

BuyJudge는 투자 추천기가 아니라, 매매 판단을 줄여주는 분석 보조 시스템이다. 목표는 감으로 종목을 고르는 일을 줄이고, 데이터·패턴·유사사례·리스크를 기준으로 후보를 좁히는 것이다.

## 1. 최종 목표

BuyJudge의 최종 목표는 다음 순서로 간다.

1. 전체 감시군 수집
2. 빠른 필터로 후보 축소
3. 후보만 유사차트 통계 분석
4. 현재가 매수 가능 / 눌림대기 / 관망 / 위험차단 / 통계부족 판정
5. 분할매수·손절·익절 플랜 생성
6. 웹 화면에서 바로 확인
7. 가상매매 기록
8. 충분히 검증된 뒤에만 자동주문 검토

## 2. 개발 원칙

### 2.1 자동주문보다 판단기 우선

초기 목표는 자동주문이 아니다.

- 지금 사도 되는지
- 눌리면 볼 종목인지
- 위험해서 제외해야 하는지
- 통계가 부족한지

이걸 먼저 안정적으로 판정한다.

### 2.2 감이 아니라 후보 축소

BuyJudge는 모든 종목을 맞히는 도구가 아니다. 종목을 줄이는 도구다.

전체 종목 → 빠른 필터 → 정밀분석 후보 → 최종판정

이 흐름을 유지한다.

### 2.3 현재가 추격매수 금지

점수와 유사통계가 좋아도 손절폭이 넓거나 손익비가 낮으면 매수후보가 아니다.

다만 버릴 종목이 아니라면 `눌림대기`로 분류한다.

### 2.4 리스크 차단은 강하게

아래 조건은 강하게 본다.

- 손절폭 15% 초과
- 손익비 1.1 미만
- 최근 5거래일 20% 이상 급등
- 20일선 대비 과열
- 60일선 아래 약세
- 동전주/페니주

### 2.5 유사사례는 억지로 채우지 않는다

유사도 낮은 사례를 억지로 30개 채우면 통계가 왜곡된다.

기본 기준:

- 유사도 55% 이상만 통계 반영
- 유사사례 최소 8건 이상
- 유사사례 부족 시 `통계부족`

### 2.6 결과는 화면에서 바로 확인한다

개발자는 CSV를 보더라도, 사용자는 웹 화면에서 봐야 한다.

현재 구조:

- `main.py`: 분석 엔진
- `app.py`: Streamlit 웹 화면
- `report.py`: HTML 리포트 생성
- `outputs/*.csv`: 분석 결과

## 3. 개발 절차

### 3.1 기능 추가 전 기준 정의

새 기능을 만들기 전에 다음을 정한다.

1. 이 기능이 어떤 문제를 줄이는가
2. 어떤 입력 데이터를 쓰는가
3. 어떤 컬럼으로 결과가 나오는가
4. 최종판정에 어떤 영향을 주는가
5. 실패 시 어떻게 처리하는가

### 3.2 작은 단위로 개발

한 번에 큰 기능을 붙이지 않는다.

나쁜 방식:

- 뉴스 + 자동주문 + 백테스트 + 화면 전부 한 번에 추가

좋은 방식:

- 데이터 컬럼 추가
- 판정 기준 추가
- 화면 표시 추가
- 결과 검토
- 기준 조정

### 3.3 실행 후 결과 검토

기능을 추가하면 다음 파일을 확인한다.

- `outputs/data_status.csv`
- `outputs/fast_scan.csv`
- `outputs/similar_scan.csv`
- `outputs/similar_cases_raw.csv`

확인 기준:

- 데이터 수집 실패가 없는가
- 매수후보가 너무 많이 나오지 않는가
- 위험차단이 합리적인가
- 눌림대기가 현실적인 가격인가
- 유사사례가 진짜 비슷한가

### 3.4 화면 검토

웹앱에서 확인한다.

- 매수후보가 먼저 보이는가
- 눌림대기가 이해되는가
- 위험차단 사유가 짧고 명확한가
- 표가 너무 개발자용이지 않은가

## 4. 판정 체계

### 4.1 매수후보

조건식, 유사통계, 리스크가 모두 통과한 상태.

기본 조건:

- 빠른 필터 점수 70점 이상
- 유사사례 최소 8건 이상
- 평균 유사도 55% 이상
- 20일 상승확률 55% 이상
- 20일 평균수익 1% 이상
- 손익비 1.1 이상
- 거래대금 20일비 0.8배 이상
- 강제 차단 사유 없음

### 4.2 눌림대기

현재가 매수는 위험하지만, 특정 가격까지 눌리면 손익비가 좋아지는 상태.

예:

- 현재가 손익비 낮음
- 손절폭 넓음
- 유사통계는 나쁘지 않음
- 눌림 진입가에서 손익비 개선

### 4.3 조건부관망

일부 조건은 괜찮지만 확실하지 않은 상태.

예:

- 유사통계는 괜찮으나 거래대금 부족
- 점수는 괜찮으나 기대수익이 낮음
- ETF처럼 안정적이지만 강한 후보는 아님

### 4.4 위험차단

현재 구조상 매수 판단에서 제외해야 하는 상태.

예:

- 손절폭 과도
- 손익비 낮음
- 급등 후 추격 위험
- 추세 약세
- 과열

### 4.5 통계부족

조건식은 볼 만하지만 유사사례가 부족한 상태.

이 경우 바로 매수판단을 내리지 않는다.

## 5. 브랜치/커밋 기준

현재는 단순 운영을 위해 `main`에 직접 반영한다. 기능이 커지면 브랜치를 분리한다.

커밋 메시지 기준:

- `Add ...`: 새 기능 추가
- `Fix ...`: 오류 수정
- `Improve ...`: 기존 기능 개선
- `Refactor ...`: 구조 정리
- `Docs ...`: 문서 수정

## 6. 금지사항

아래는 하지 않는다.

- 검증 없이 자동주문 연결
- 유사도 낮은 사례로 승률 포장
- 매수후보를 많이 만들기 위해 기준 완화
- 한 번의 결과만 보고 로직 확정
- 뉴스 키워드만 보고 매수후보 승격
- 실패한 데이터 수집을 조용히 무시

6. CSV로 원인 확인
7. 기준 수정
8. 반복
